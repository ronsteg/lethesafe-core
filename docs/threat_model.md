# Threat Model

This document describes the threat model assumed by the Lethesafe project.
It clarifies which attack scenarios are addressed by the design and which
are explicitly out of scope.

Lethesafe is not a general-purpose security solution. It is a focused
tool that enforces an unavoidable delay before access becomes possible.


## Security Objective

The primary security objective of Lethesafe is:

To ensure that access to a protected target value becomes possible
only after a defined amount of sequential computation time has elapsed.

This delay must not be bypassable by shortcuts, parallelization,
or alternative execution strategies.


## Protected Assets

Lethesafe protects the following assets:

- The enforced time delay before access becomes possible
- The integrity of the time-lock computation
- The reproducibility and verifiability of the computation result

Lethesafe does not directly protect user data, secrets, or payloads.
It delays access to values required to unlock or derive them.


## Assumptions

Lethesafe relies on the following assumptions:

- The hash function used is sequential and cannot be efficiently parallelized
- The execution environment performs the computation as specified
- The attacker cannot retroactively shorten elapsed real time
- The attacker does not possess precomputed results for the specific puzzle

These assumptions are intentionally explicit and minimal.


## In-Scope Threats

The following threats are considered in scope:

- Theft or coercion before the time delay has elapsed
- Attempts to accelerate computation using parallel hardware
- Attempts to skip or shortcut the sequential computation
- Attempts to modify puzzle parameters without detection

The design aims to make these attacks ineffective or impractical.


## Out-of-Scope Threats

The following threats are explicitly out of scope:

- Compromise of the execution environment (malware, root access)
- Side-channel attacks on the executing hardware
- User error or misuse of the tool
- Loss or improper handling of files generated by Lethesafe
  (e.g. time capsules or derived outputs) after computation completes
- Attacks occurring after the time delay has fully elapsed

Lethesafe assumes that the user controls the execution environment
during the computation phase.


## Non-Goals

Lethesafe does not aim to:

- Provide confidentiality through encryption
- Hide the existence of protected data
- Prevent access after the time delay has elapsed
- Replace secure storage or key management systems

Its sole function is to introduce a reliable and unavoidable delay.


## Design Implications

These threat model assumptions lead to the following design decisions:

- Simplicity over complexity
- Deterministic and auditable computation
- No reliance on external services or infrastructure
- Clear separation between delay enforcement and data protection


## Summary

Lethesafe enforces time as a security factor.

It does not rely on secrecy, obscurity, or trust in external parties.
Its guarantees are limited, explicit, and verifiable.

Understanding these limits is essential for correct and safe use.
